Un proyecto de Crono ETL es una carpeta con ficheros de texto: el código Crono SQL de cada tabla, las acciones que mueven y orquestan los datos y la configuración del proyecto. Al ser texto, el proyecto entero puede versionarse en Git y revisarse como cualquier otro código.

Salvo la carpeta `.crono`, en la que Crono busca la configuración, la organización de las carpetas es una convención: el código no depende de ella. Aun así, recomendamos seguir esta estructura, que hemos aplicado en todos nuestros proyectos y que resultará familiar a quien haya trabajado con otras herramientas de transformación de datos.

## Estructura recomendada

<FileTree>

- .crono/
  - config.jsonc propiedades del proyecto
  - declarations/ declaraciones del proyecto
    - strategies.sql
    - vv_erp.sql
  - environments/ un fichero por entorno
    - dev.jsonc
    - prod.jsonc
- jobs/ lo que se ejecuta sobre el DWH: workflows, cargas, comprobaciones…
  - dwh_load.job
  - bulk_ERP.job
  - final_checks.sql
  - …
- models/ un fichero por tabla o vista
  - stg_erp.orders_all_companies.sql
  - dwh.customers.sql
  - dwh.products.sql
  - dwh.invoices.sql
  - …
- seeds/ ficheros de entrada mantenidos a mano
  - account_groups.csv
  - budget.xlsx
- catalogs/ catálogos de Crono Metadata
- docs/ documentación del proyecto
- scratch/ consultas de prueba, fuera de Git
- Crono.etlproj preferencias del IDE de Crono ETL para Windows

</FileTree>

## Carpetas y ficheros

| Elemento | Contenido |
| --- | --- |
| `.crono/config.jsonc` | Las [propiedades del proyecto](/etl/configuration/project/): campos de auditoría, cuenta de Calendas, ficheros de declaraciones… |
| `.crono/declarations/` | Las declaraciones del proyecto: estrategias y vistas virtuales. Consulta [Declaraciones](#declaraciones). |
| `.crono/environments/` | Un fichero por entorno, con el nombre del entorno (`dev.jsonc`, `prod.jsonc`…). Cada uno define las [conexiones](/etl/configuration/connections/), los [almacenamientos](/etl/configuration/storage/) y las [credenciales](/etl/configuration/credentials/) de ese entorno. Los secretos se guardan encriptados. |
| `jobs/` | Todo lo que se ejecuta sobre el DWH sin formar parte de él: [workflows](/etl/orchestration/workflow/), cargas con [BULK TABLE](/etl/data-movement/bulk-table/), exportaciones, comprobaciones, tareas de mantenimiento… Consulta [Modelos y trabajos](#modelos-y-trabajos). El IDE muestra en el panel lateral los trabajos de esta carpeta. |
| `models/` | El código Crono SQL que crea y carga cada tabla o vista del DWH. Consulta [Nombres de los modelos](#nombres-de-los-modelos). |
| `seeds/` | Ficheros de entrada que se mantienen a mano, como jerarquías, tablas de correspondencia o presupuestos. Admite tanto CSV como Excel, y los ficheros los leen los propios modelos (consulta [Datos externos](/etl/transformation/external-data/)). |
| `catalogs/` | Los catálogos creados con Crono Metadata, que consumen Crono Analysis o el MCP de Crono. Todos los catálogos deben estar en la misma carpeta, porque Crono Server los busca en ella. |
| `docs/` | Documentación del proyecto, tanto la propia como la que proporciona el cliente. |
| `scratch/` | Consultas de prueba o de exploración, que no forman parte del proyecto. Así no quedan ficheros como `test.sql` o `delete_me.sql` en la raíz. |
| `Crono.etlproj` | Preferencias del IDE de Crono ETL para Windows, como la carpeta de trabajos o los paneles visibles. Crono CLI no lo utiliza. |

Los nombres de las carpetas se escriben en minúsculas. Windows no distingue mayúsculas de minúsculas, pero Git y Linux sí, y un proyecto puede acabar ejecutándose con Crono CLI desde un repositorio.

## Modelos y trabajos

La frontera entre `models/` y `jobs/` es sencilla: en `models/` está el DWH; en `jobs/`, lo que se le hace al DWH.

- **`models/`** contiene los objetos que forman el DWH: cada tabla o vista, con su carga.
- **`jobs/`** contiene todo lo demás: workflows, cargas con BULK TABLE, comprobaciones, validaciones, tareas de mantenimiento, exportaciones… Da igual que sean ficheros `.job` (acciones que Crono ejecuta fuera de la base de datos) o `.sql` (código que se ejecuta en ella), o que creen un procedimiento o no: la extensión ya indica dónde se ejecuta cada fichero.

Para decidir dónde va un procedimiento, cuenta las tablas que modifica, no las que lee. Si modifica una sola tabla, forma parte de su modelo y va en `models/` (consulta [Procedimientos que actualizan un modelo](#procedimientos-que-actualizan-un-modelo)). Si modifica varias, o ninguna, como las comprobaciones que solo leen, va en `jobs/`.

## Nombres de los modelos

Cada fichero de `models/` crea o carga un único objeto, y se llama igual que él: `esquema.tabla.sql`. El IDE guarda los ficheros con ese nombre sin preguntar. Aunque el nombre no afecta al código, conviene respetarlo siempre: basta con saber qué tabla se busca para saber en qué fichero está.

El esquema indica la capa del DWH a la que pertenece el objeto:

| Esquema | Contenido |
| --- | --- |
| `stg_<origen>` | Staging: los datos tal como llegan de cada origen, por ejemplo `stg_erp` o `stg_crm`. |
| `dwh` | El modelo final, que consultan las herramientas de análisis. |

Las tablas de staging que carga una acción [BULK TABLE](/etl/data-movement/bulk-table/) no necesitan un fichero, porque las crea la propia acción. En `models/` solo aparecen los objetos de staging que se construyen a partir de esas tablas; por ejemplo, la tabla que reúne en una sola las tablas de pedidos de varias empresas.

### Procedimientos que actualizan un modelo

Toda la lógica de carga de una tabla debe estar en su fichero de modelo, en una única consulta. Es la regla más importante de la estructura del proyecto: quien abre `dwh.invoices.sql` debe ver todo lo que determina el contenido de esa tabla, sin buscarlo en otros ficheros.

Excepcionalmente, una actualización no puede expresarse dentro de la carga; por ejemplo, un cálculo complejo que depende de los datos ya cargados. En ese caso:

- Se crea un procedimiento aparte, en `models/`, que actualiza **solo** esa tabla. Cada fichero sigue conteniendo una única instrucción: el modelo, el procedimiento que carga la tabla; el nuevo fichero, el procedimiento que la actualiza.
- El nombre del procedimiento, y por tanto el del fichero, empieza por el nombre del modelo que actualiza: `dwh.invoices_margins.sql` actualiza `dwh.invoices`. Así, ordenados alfabéticamente, aparecen juntos.
- Un comentario al principio del fichero explica por qué esa lógica no puede formar parte de la carga.

:::caution
Antes de crear uno de estos procedimientos, intenta incorporar la lógica a la carga. Cada excepción obliga a abrir más de un fichero para entender una tabla.
:::

### Subcarpetas

Mientras haya pocas tablas, lo más cómodo es dejar todos los modelos en la raíz de `models/`: como el nombre de cada fichero empieza por su esquema, al ordenarlos alfabéticamente quedan agrupados por esquema.

Si el proyecto crece, pueden organizarse en subcarpetas, por ejemplo una por esquema. En ese caso, conviene que el fichero conserve el esquema en su nombre (`models/stg/stg.invoices.sql`, no `models/stg/invoices.sql`): así sigue identificando la tabla por sí solo, en el editor, en una búsqueda o en un cambio de Git, y no depende de la carpeta en la que esté.

El mismo criterio vale para `jobs/`: mientras haya pocos trabajos, en la raíz; si su número crece, pueden agruparse en subcarpetas como `bulk/` o `export/`.

## Declaraciones

Las estrategias y las vistas virtuales son declaraciones: no se ejecutan ni crean nada en la base de datos, sino que Crono las reconoce y las sustituye al transpilar. Se declaran para todo el proyecto, y pueden usarse en cualquier fichero.

Por eso se guardan en `.crono/declarations/`, junto a la configuración que Crono lee antes de empezar, y no entre los modelos:

- Las estrategias, en `strategies.sql`.
- Las vistas virtuales, en un fichero por esquema, con el nombre del esquema: `vv_erp.sql` declara las vistas `vv_erp.*`. Lo habitual es que sean las consultas que una acción [BULK TABLE](/etl/data-movement/bulk-table/) lanza contra un origen; si el esquema virtual se corresponde con el de destino (`vv_erp` → `stg_erp`), basta con ver el fichero para saber qué staging alimenta.

Cada fichero debe darse de alta en `declaration-locations`, en las [propiedades del proyecto](/etl/configuration/project/).

Excepcionalmente, una carga compleja puede apoyarse en una vista virtual que solo usa ella, para dividir el proceso en pasos. Como en los [procedimientos que actualizan un modelo](#procedimientos-que-actualizan-un-modelo), el nombre del fichero empieza por el del modelo que la usa, y se explica en un comentario por qué la lógica no está en la carga.

## Control de versiones

Se versiona todo el proyecto, salvo la carpeta `scratch/`. Se recomienda excluir también el fichero del entorno de producción, de modo que sus secretos no lleguen al repositorio. Un `.gitignore` como este en la raíz del proyecto cubre ambos casos:

```
scratch/
.crono/environments/prod.jsonc
```
